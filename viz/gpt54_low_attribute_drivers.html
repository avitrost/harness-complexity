Which harness attributes seem to drive the small-model lift?

Exploratory analysis for gpt-5.4-mini low on the TB2 9-task subset, excluding minimal-agent and terminus-2-compressed.

CSV outputs: /wbl-fast/usrs/trost/harness-complexity/final_test/behavior_gpt54_low_family_20260612/attribute_driver_analysis

Most stable signal Session handling plus multi-call/replay mechanics is the only feature family that survives the task-fixed and leave-one-task-out checks.
Secondary signal Read/search plus a bounded edit/execute loop helps. Repeated editing or scripting by itself looks more like struggle than capability.
Weak signal LOC, input tokens, output tokens, and total command count are weaker and less stable than the mechanics features.

Caveat

This is not causal identification. The sample is small, many harness features are correlated, and action counts are partly downstream of the model's behavior. The goal is to narrow plausible mechanisms, not to prove one variable independently causes the whole lift.

What The Terms Mean

By recoverable stateful interaction, I mean a harness that gives the model a durable enough interaction loop to recover from a bad command: it can see the command output or error, keep track of prior tool calls, adjust the next action, and continue without having to reconstruct the whole state from scratch. In these logs this is not one primitive; it is a bundle of mechanics that make the next step better informed after each shell action.

Session commands Counted when a shell turn has metadata.unified_exec.session_id. Practically, this means the harness is using a persistent execution session rather than only isolated one-shot shell calls. That can preserve useful process/session state such as current shell context, active subprocesses, or interactive continuity.
Multi-call turns Counted when Codex metadata reports codex_emitted_tool_calls > 1. This means one model response produced multiple tool calls instead of a single command. It is a proxy for a harness that lets the model express a small sequence of operations in one reasoning step.
Response replay turns Counted when a turn includes mini_swe_agent_v2_messages or codex_response_items metadata. This means the harness is preserving or replaying structured assistant/tool-call history around the command, rather than logging only the raw shell command. It helps the next model call retain the action/observation chain.
Session + multi-call + replay The combined metric used in the regressions: mean_session_commands + mean_multi_call_turns + mean_response_replay_turns. It should be read as a proxy for interaction scaffolding, not as a literal causal variable. It captures whether the harness supports continuity, batched/planned actions, and trace replay.

So the claim is not "state" in the philosophical sense, and not just "the model has a longer prompt." The concrete claim is: the small model does better when the harness makes the action/observation loop recoverable enough that failed commands and partial results become useful information for the next action.

More explicitly: most files written to /app persist even in a non-persistent shell, so the likely benefit is not just "the file system keeps state." The helpful pieces appear to be: keeping the command/observation history structured, letting the model continue after errors, allowing multiple related tool calls in one response, and, when needed, preserving a live shell session for ongoing processes or interactive continuations.

Working Interpretation

The most likely driver is recoverable stateful interaction: the model benefits when the harness preserves enough interaction structure for it to recover from partial failures and continue an inspect-edit-execute loop. The second driver is context acquisition without thrash: read/search is useful, while high edit/script volume without the stateful loop often marks wandering. Test-like checks help when present, but they are not the whole story because some high-scoring Codex rows have few explicit test commands.
